### Aether 0.841.0 and aephysics ce2ea25

- **`AETHER_REF` v0.834.0 to v0.841.0.** ae3d was held at 0.834.0 since
  2026-10-20, for two reasons. aephysics b37fae2 and later put AVX2 copies
  into every x86 build, and before 0.836.0 GCC on Win64 hit an internal
  compiler error on those at -O0 (expand_one_stack_var_1, aether#3023).
  aephysics f0bd6d6 does not build on 0.835+.
  - aephysics moves to ce2ea25, its main. It passes its own suite and
    golden trace on 0.841.0. Its test_parallel failed about four runs in
    ten on an idle M6 (one pool thread took every block), so its check now
    waits for any second worker.
  - The ownership rules of 0.836 to 0.839 are on Nic's feat/aether-0839:
    @into accessors, @keep fn slots, closures against `null`, and kept
    struct parameters.
  - 0.840.0 treats a borrowed ptr put in a list or a map as kept.
    `skin.skeleton_add_mesh` and the texture worker's done closure declare
    @keep, and the net makers are `@keep fn`.
  - Audio's start phase lists the state its component holds, not the
    borrowed argument. A phase is a C function pointer.
  - 0.841.0 parenthesises a closure's `== null` condition once
    (aether#3123), which on 0.840.0 was a clang -Wparentheses-equality in
    the net module.
  - No E0305 (one export name per operation) and no E0202 (was W1005) in
    ae3d. All 266 programs compile on 0.841.0 without an error or a
    warning.
- **`AETHER_UI_REF` c55a375a to ac75c750** (aether-ui#221). The toolkit's
  kept fn and ptr parameters declare @keep, so `ui` compiles on 0.840.0.
  The editor's inspector slots are typed `fn(ptr, @keep ptr, ...)` for the
  object that component_edited and component_structure keep.
- **`AETHER_UI_REF` ac75c750 to 51d1ae75** (the linux-editor job on #864).
  ac75c750 carries ebee1c96, which settles the layout before each driver
  request by running the main loop up to 32 rounds. The editor's frame timer
  is due again the moment a frame ends, so every round was a frame, and after
  Add Terrain a frame is 250 ms on lavapipe: a request took eight seconds,
  the drive's 3 s timeout fired and the abandoned requests queued up, so the
  drive made no more progress and ran to its 900 s backstop. The editor was
  not hung (its frame counter kept rising, 4 a second). 51d1ae75 bounds the
  settling at 30 ms; its `settle_demo` spec reads 361 ms a request where
  ac75c750 reads 4095. Main passed because it pins dcc1bd48, which predates
  the settling.
- **A frame's fence is waited on for 30 s at most** (`vkframe.wait_fence`).
  `frame_wait` and the wait at the start of a frame were vkWaitForFences with
  no timeout; one that runs out now fails the read, records a device error
  naming the frame, the fence's status and how often each slot was begun and
  submitted, prints it, and stops later waits from costing the same again.
  `tests/test_vk_fence_wait`.
